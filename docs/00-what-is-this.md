# מה הפרויקט הזה עושה — לפני שנכנסים לקוד

> המדריך הזה נכתב כדי שכל אחד — גם בלי רקע בתכנות — יוכל להבין מה המערכת הזו,
> למה כל חלק בה קיים, ואיך להגן על כל החלטה בה. אין כאן ז'רגון בלי הסבר.

---

## הבעיה שהמערכת הזו פותרת

אחרי ה-7 באוקטובר, קהילת **קיבוץ כיסופים** פונתה למלון. כל התקשורת עברה
לקבוצות וואטסאפ — ותוך ימים זה הפך לזרם בלתי-נגמר של הודעות. הודעה חשובה על
הסעה או תרופה נבלעה בין מאות הודעות אחרות. אי אפשר היה למצוא כלום.

**המערכת הזו הופכת את זרם הצ'אט למבנה מסודר:** הודעות נכנסות לקטגוריות
("הסעות", "בריאות", "אבידות ומציאות"), ואפשר לחפש, לסנן, ולמצוא.

זו לא אפליקציית צ'אט. זו מערכת **ארגון וחיפוש** של מידע קהילתי.

---

## מה יש כאן, בתמונה אחת

המערכת בנויה משלושה חלקים נפרדים שמדברים ביניהם:

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  אפליקציית   │     │    לוח        │     │  זה הריפו:    │
│  המשתמש      │────▶│    ניהול      │────▶│  ה־Backend    │
│  (React)     │     │   (React)     │     │  (Node.js)   │
└──────────────┘     └──────────────┘     └──────┬───────┘
   מה שהתושב             מה שמנהל              │
   רואה                  הקהילה עורך            │
                                          ┌──────┴───────┐
                                          │              │
                                    ┌─────▼────┐   ┌─────▼────┐
                                    │ MongoDB  │   │   AWS    │
                                    │          │   │   S3     │
                                    │ הטקסט:   │   │ הקבצים:  │
                                    │ הודעות,  │   │ תמונות,  │
                                    │ קטגוריות,│   │ מסמכים   │
                                    │ משתמשים  │   │ מצורפים  │
                                    └──────────┘   └──────────┘
```

**המונחים, בשפה פשוטה:**

| מונח | מה זה, באנלוגיה |
|---|---|
| **Backend** | המוח מאחורי הקלעים. אין לו מסך — הוא רק מקבל בקשות ומחזיר תשובות. הריפו הזה. |
| **Frontend** | מה שרואים בדפדפן. שולח בקשות ל-Backend. (ריפו נפרד) |
| **API** | "התפריט" של ה-Backend — רשימת הבקשות שמותר לבקש ממנו |
| **MongoDB** | ארון תיוק לטקסט. מחזיק את ההודעות, הקטגוריות והמשתמשים |
| **AWS S3** | מחסן לקבצים. תמונה או PDF מצורף להודעה נשמר שם, לא ב-MongoDB |

---

## למה טקסט ב-MongoDB אבל קבצים ב-S3?

זו שאלה ששאלת בעצמך, והתשובה היא עיקרון תכנוני אמיתי:

**מסדי נתונים גרועים באחסון קבצים גדולים.** MongoDB מצוין למצוא "כל ההודעות
בקטגוריית הסעות מהשבוע" — חיפוש מהיר על טקסט. אבל תמונה של 3 מגה-בייט? היא
תנפח את המסד, תאט כל חיפוש, ותייקר את הגיבויים.

**S3 בנוי בדיוק לזה:** אחסון זול של קבצים, שכל אחד מקבל כתובת. אז:

- ב-MongoDB נשמר **המצביע** לקובץ (מפתח קצר, כמו `messages/a3f8...`)
- ב-S3 נשמר **הקובץ עצמו**

כשמישהו פותח הודעה עם תמונה, ה-Backend מבקש מ-S3 **קישור זמני** לתמונה
(תקף 60 דקות) ומצרף אותו לתשובה. כך הקבצים אף פעם לא ציבוריים לגמרי — צריך
לעבור דרך ה-Backend כדי לקבל קישור.

זה בדיוק מה שכתוב ב-`src/services/s3.js`.

## שלושת סוגי המידע (ה"ישויות")

כל המערכת סובבת סביב שלושה דברים:

1. **הודעה (Message)** — פריט מידע יחיד. יש לו כותרת, טקסט, קטגוריה שהוא שייך
   אליה, מי שלח אותו, ואולי קובץ מצורף.

2. **קטגוריה (Category)** — הקבוצה שהודעות מתארגנות לפיה. "הסעות", "בריאות".
   מנהל הקהילה יוצר אותן; תושב רגיל לא.

3. **משתמש (User)** — מי שמשתמש במערכת. יש לו אימייל, סיסמה (מוצפנת), ו**תפקיד**:
   `member` (תושב רגיל) או `admin` (מנהל קהילה). התפקיד קובע מה מותר לו.

זכור את שלושת אלה — כל שאר המדריכים בנויים סביבם.
