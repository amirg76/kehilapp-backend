# מדריך משתמש ותהליכים — מי יכול לעשות מה

> **מה המדריך הזה עונה עליו:** מבט מעשי מלמעלה — מי הם המשתמשים, מה כל אחד
> יכול לעשות, ומה קורה מאחורי הקלעים בכל פעולה. בלי קוד, רק תהליך.

---

## שני סוגי משתמשים

| | **חבר (member)** | **מנהל (admin)** |
|---|---|---|
| מי זה | תושב הקהילה | מי שמנהל את התוכן |
| קורא הודעות | ✅ | ✅ |
| כותב הודעה | ✅ | ✅ |
| עורך הודעה | ✅ **רק שלו** | ✅ כל הודעה |
| מוחק הודעה | ❌ | ✅ |
| מוחק את כל ההודעות | ❌ | ✅ |
| יוצר/עורך קטגוריות | ❌ | ✅ |
| רואה את רשימת כל המשתמשים | ❌ | ✅ |

**העיקרון:** חבר יכול לתרום תוכן ולנהל את **שלו**. מנהל מנהל את **המבנה** —
קטגוריות, מחיקות, משתמשים. זה בדיוק חלוקת ה-`requireRole` בקוד.

## מפת ה-API המלאה

כל שורה כאן היא בקשה אמיתית שהמערכת מקבלת. ה"שומרים" הם מה שרץ לפני שהבקשה
מגיעה ליעד.

| בקשה | מה היא עושה | שומרים |
|---|---|---|
| `POST /api/auth/login` | התחברות, מחזיר טוקן | 🌐 ציבורי + הגבלת קצב מוגברת |
| `GET /healthz` | "השרת חי?" | 🌐 ציבורי |
| `GET /readyz` | "השרת מוכן?" | 🌐 ציבורי |
| `GET /api/messages` | רשימת הודעות (מעומדת) | 🔑 אימות |
| `GET /api/messages/:id` | הודעה בודדת | 🔑 אימות |
| `POST /api/messages` | הודעה חדשה | 🔑 אימות |
| `PATCH /api/messages/:id` | עריכת הודעה | 🔑 אימות + בעלות |
| `DELETE /api/messages/:id` | מחיקת הודעה | 🔑 אימות + 👑 מנהל |
| `DELETE /api/messages` | מחיקת כל ההודעות | 🔑 אימות + 👑 מנהל |
| `GET /api/categories` | רשימת קטגוריות | 🔑 אימות |
| `GET /api/categories/:id` | קטגוריה בודדת | 🔑 אימות |
| `POST /api/categories` | קטגוריה חדשה | 🔑 אימות + 👑 מנהל |
| `PATCH /api/categories/:id` | עריכת קטגוריה | 🔑 אימות + 👑 מנהל |
| `DELETE /api/categories/:id` | מחיקת קטגוריה | 🔑 אימות + 👑 מנהל |
| `GET /api/users` | כל המשתמשים | 🔑 אימות + 👑 מנהל |
| `GET /api/users/:id` | משתמש בודד | 🔑 אימות |

**מקרא:** 🌐 ציבורי · 🔑 צריך טוקן · 👑 צריך תפקיד מנהל

## תהליך מלא #1: תושב מתחבר וקורא הודעות

```
1. התושב פותח את האפליקציה, מקליד אימייל + סיסמה, לוחץ "התחבר"
        │
2. האפליקציה שולחת:  POST /api/auth/login
        │
3. השרת:
   • מגביל קצב — יותר מ-10 ניסיונות כושלים? חסום ל-15 דקות
   • מוצא את המשתמש, משווה סיסמה מול הטביעה המוצפנת
   • תקין → מנפיק טוקן (תקף 12 שעות) ומחזיר
        │
4. האפליקציה שומרת את הטוקן ומבקשת הודעות:
   GET /api/messages    (עם הטוקן בכותרת)
        │
5. השרת:
   • בודק את הטוקן (מי אתה?) → תקין
   • שולף עד 50 הודעות מ-MongoDB, החדשות first
   • לכל הודעה עם קובץ — מבקש מ-S3 קישור זמני (60 דק')
   • מחזיר את הרשימה + כמה יש בסך הכל (בכותרת)
        │
6. התושב רואה את ההודעות, יכול לחפש ולסנן לפי קטגוריה
```

## תהליך מלא #2: תושב כותב הודעה עם תמונה

```
1. התושב ממלא כותרת, טקסט, בוחר קטגוריה, מצרף תמונה
        │
2. POST /api/messages   (עם הטוקן + הקובץ)
        │
3. השרת, בסדר הזה:
   • בודק טוקן (מי אתה?)
   • בודק את הקובץ (multer): תמונה או PDF? עד 5MB? SVG נחסם.
     ← שימו לב: הבדיקה קורית *אחרי* האימות. אנונימי לא מגיע עד לכאן,
       אז אף אחד לא יכול למלא לנו את S3 בלי להיות מזוהה.
   • שומר את הקובץ ב-S3, מקבל מפתח
   • שומר את ההודעה ב-MongoDB עם:
     – השולח (senderId) — נלקח *מהטוקן*, לא ממה שהתושב שלח.
       ככה אי אפשר להתחזות למישהו אחר.
     – המפתח ל-S3
        │
4. ההודעה נוצרה, חוזרת לתושב
```

## תהליך מלא #3: תושב מנסה לערוך הודעה של אחר (ונחסם)

זה התהליך שמדגים את תיקון ה-IDOR:

```
1. תושב א' רואה הודעה של תושב ב', רוצה לשנות אותה
        │
2. PATCH /api/messages/[מזהה ההודעה של ב']
        │
3. השרת:
   • בודק טוקן → א' מזוהה כדין
   • מנסה לעדכן — אבל השאילתה מוגבלת:
     "עדכן הודעה עם המזהה הזה *ורק אם* השולח הוא א'"
   • ההודעה שייכת לב', לא לא' → לא נמצאה התאמה
   • מחזיר 404 (כאילו ההודעה לא קיימת)
        │
4. ההודעה של ב' לא השתנתה. א' לא יכול לגעת בה.

   (אם א' היה מנהל — התנאי היה נופל, ומנהל יכול לערוך הכל)
```

## מה קורה כשמשהו משתבש

המערכת לא קורסת על שגיאות. כל שגיאה מקבלת תשובה ברורה וקוד מתאים:

| מצב | קוד | מה המשתמש מקבל |
|---|---|---|
| הכל תקין | 200 | המידע המבוקש |
| בקשה בנויה לא נכון | 400 | "Validation Error" |
| אין טוקן / טוקן פג | 401 | "Unauthorized" |
| מזוהה, אבל אין הרשאה | 403 | "Forbidden" |
| לא נמצא / לא שלך | 404 | "Not Found" |
| יותר מדי בקשות | 429 | "Too Many Requests" |
| באג בשרת | 500 | "Internal Server Error" (בלי לחשוף פרטים) |

**נקודה חשובה:** בשגיאת 500, המשתמש מקבל הודעה כללית בלבד. הפרטים המלאים
נרשמים בלוג של השרת — אבל **לעולם** לא נשלחים למשתמש, כי הם עלולים לחשוף
מבנה פנימי שתוקף ישמח לקבל.
